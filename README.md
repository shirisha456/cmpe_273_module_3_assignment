# CMPE 273 Module 3 – REST & gRPC Service Contracts

## 1. Overview

This project implements the same **Order Service → Inventory Service** interaction twice, once with REST and once with gRPC, both in Python.

- **Order Service** accepts an order (`item_id`, `quantity`) from a client and asks the Inventory Service whether it can be fulfilled.
- **Inventory Service** checks a hard-coded in-memory inventory and says whether the item and quantity are available.
- **REST version**: Flask services talking HTTP + JSON. The Order Service calls Inventory with `requests` and a **1 second timeout**.
- **gRPC version**: the Inventory Service is a gRPC server defined by `inventory.proto`. The Order Service is a small Flask app with the same `/v1/orders` and `/health` endpoints, and it calls Inventory through the generated gRPC stub with a **1 second deadline**.

Both versions use the same business rules:

| Request | Result |
|---|---|
| `sku-123`, quantity 1–7 | available |
| `sku-123`, quantity > 7 | unavailable (insufficient quantity) |
| unknown item (e.g. `sku-999`) | unavailable (not found) |
| missing/invalid fields, quantity ≤ 0 | invalid input |

Inventory: `sku-123 → 7` (in memory, no database).

```text
REST:                                gRPC:

Client (curl)                        Client (curl)
  │  HTTP + JSON                       │  HTTP + JSON
  ▼                                    ▼
Order Service      :8080             Order Service      :8090
  │  HTTP + JSON (timeout=1s)          │  gRPC + Protobuf (deadline=1s)
  ▼                                    ▼
Inventory Service  :8081             Inventory Service  :50051
```

**Ports**

| Service | Port |
|---|---|
| REST Order Service | 8080 |
| REST Inventory Service | 8081 |
| gRPC Order Service (HTTP front end) | 8090 |
| gRPC Inventory Service | 50051 |

> Port 5000 was not used because macOS reserves it for AirPlay Receiver.

# REST Version

## API

**Inventory Service** – `POST /v1/inventory/check`

```json
{ "item_id": "sku-123", "quantity": 2 }
```

**Order Service** – `POST /v1/orders` (same body). It forwards `item_id` and `quantity` as JSON to the Inventory Service with `timeout=1`.

Both services expose `GET /health` → `200 {"status":"ok"}`.

### HTTP status codes

| Situation | Inventory Service | Order Service | Why |
|---|---|---|---|
| Item available | 200 | 200 | normal success |
| Malformed / invalid input | 400 | 400 | the client sent a bad request |
| Unknown item | 404 | 404 | the requested resource (item) doesn't exist |
| Not enough quantity | 409 | 409 | the request is valid but conflicts with current inventory state |
| Inventory too slow (timeout) | – | **504 Gateway Timeout** | the upstream dependency didn't answer in time |
| Inventory not running | – | **503 Service Unavailable** | the dependency is unreachable |
| Inventory returned non-JSON | – | 502 Bad Gateway | the dependency gave a bad response |

The Order Service passes 400/404/409 from Inventory straight through, so the client sees *why* the order was rejected.

## Running the REST version

**Terminal 1 – Inventory Service**
```bash
cd rest
python inventory_service.py
```

**Terminal 2 – Order Service**
```bash
cd rest
python order_service.py
```

## REST timeout handling

| Setting | Value | Where |
|---|---|---|
| Order → Inventory timeout | **1 second** | `INVENTORY_TIMEOUT_SECONDS` in `rest/order_service.py` |
| Artificial inventory delay | **2 seconds** | `INVENTORY_DELAY_SECONDS` environment variable |

The Inventory Service reads the `INVENTORY_DELAY_SECONDS` environment variable (default `0`) and calls `time.sleep()` for that long before answering.

**Steps**

1. Leave the Order Service running in Terminal 2.
2. In Terminal 1, stop the Inventory Service (Ctrl+C) and restart it in slow mode:
   ```bash
   INVENTORY_DELAY_SECONDS=2 python inventory_service.py
   ```
3. Send an order:
   ```bash
   time curl -i -X POST http://127.0.0.1:8080/v1/orders \
     -H 'Content-Type: application/json' \
     -d '{"item_id":"sku-123","quantity":2}'
   ```

Actual output (returns after about 1 second, not 2):
```text

Content-Type: application/json

{"error":"inventory service timed out after 1s","status":"failed"}
  0.01s user 0.01s system 1% cpu 1.023 total
```

Order Service log:

# gRPC Version

## Contract (`grpc/inventory.proto`)

```proto
syntax = "proto3";

package inventory;

service InventoryService {
  rpc CheckInventory(InventoryRequest) returns (InventoryResponse);
}

message InventoryRequest {
  string item_id = 1;
  int32 quantity = 2;
}

message InventoryResponse {
  bool available = 1;
  string item_id = 2;
  int32 requested_quantity = 3;
  int32 available_quantity = 4;
}
```

### gRPC status codes

| Situation | gRPC status | Why | HTTP status the Order Service returns |
|---|---|---|---|
| Item available | `OK` | normal success | 200 |
| Empty `item_id` or quantity ≤ 0 | `INVALID_ARGUMENT` | the request itself is bad | 400 |
| Unknown item | `NOT_FOUND` | the item doesn't exist | 404 |
| Not enough quantity | `FAILED_PRECONDITION` | the request is valid, but inventory isn't in a state that can fulfill it | 409 |
| Inventory too slow | `DEADLINE_EXCEEDED` (raised by the client deadline) | the 1s deadline expired | 504 |
| Inventory not running | `UNAVAILABLE` | the server can't be reached | 503 |

Unavailable inventory is reported as a gRPC **error status**, not as a successful response with `available=false`. That mirrors the REST version's 404/409.

## Generating protobuf files

```bash
cd grpc
python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. inventory.proto
```

This produces `inventory_pb2.py` and `inventory_pb2_grpc.py`, which are included in this folder. No import changes were needed, because the services run from inside the `grpc/` folder.

# Failure Isolation Summary

| Step | REST (Order :8080) | gRPC (Order :8090) |
|---|---|---|
| Normal order | 200 accepted | 200 accepted (`OK`) |
| Inventory slowed to 2s | 504 after ~1.02s (`requests` timeout) | 504 after ~1.03s (`DEADLINE_EXCEEDED`) |
| `/health` right after failure | **200 `{"status":"ok"}`** | **200 `{"status":"ok"}`** |
| Inventory back to normal | 200 accepted | 200 accepted (`OK`) |

In both versions, the Order Service process was never restarted during the test. It caught the failure, returned a clean error, and kept serving requests.

# REST vs. gRPC Comparison

With REST, the contract is basically a convention: I chose the URL (`/v1/inventory/check`), the JSON field names, and which HTTP status codes mean what, and nothing enforces it except my own validation code. With gRPC, the contract lives in `inventory.proto`, and `protoc` generated typed client and server code from it, so the request and response shapes are fixed and both sides have to agree on them. Timeout handling was similar in idea but different in mechanics: in REST I passed `timeout=1` to the `requests` library and caught `requests.exceptions.Timeout`, while in gRPC I set a deadline on the RPC call and checked for the `DEADLINE_EXCEEDED` status code. Errors also felt different, because REST uses HTTP codes like 404/409/504, whereas gRPC has its own status codes like `NOT_FOUND` and `FAILED_PRECONDITION` that the server raises with `context.abort()`. Overall, gRPC gave me a stricter, typed contract with less hand-written parsing, but REST was much easier to inspect and debug by hand, since I could just curl it and read the JSON.
